Two Pointers

Two indices walk a line. Each move throws away a batch of candidates you have proved cannot be the answer. That is the whole pattern — an invariant plus a safe move rule — and it is what turns an O(n²) search over all pairs into a single O(n) pass.

Must-know tier 35–45 min 125 → 15 → 42 Builds on: sorting Feeds: sliding window
01 — why it works

Every pair is a cell in a grid

Before any code, get the picture right. A question like "which two numbers add to 19?" is a search over every pair (i, j). Lay those pairs out as cells in a grid: for six numbers there are 15 of them. Brute force visits all 15.

Two pointers starts in the top-right corner and, at every comparison, crosses off an entire row or an entire column at once. Step through it and count the cells it actually touches.

Two Sum II · sorted array, target 19 LeetCode 167

The argument, in one breath

The array is sorted ascending. Pointers sit at left and right.

  • Sum too small? nums[left] is paired with the biggest partner still available. Every other partner is smaller, so no pair using left can ever reach the target. Row eliminated — advance left.
  • Sum too big? Mirror image. nums[right] is paired with the smallest partner available, so no pair using right can work. Column eliminated — retreat right.

Nothing discarded could have been the answer, and each step moves a pointer one place, so the pointers meet after at most n steps. That is the proof and the complexity in the same sentence.

The transferable idea Every two-pointer solution is an invariant (what must stay true between the pointers) plus a move rule (which pointer advances, and the argument for why that is safe). When you meet a new problem, those are the two things to name out loud. If you cannot justify the move, you do not have a two-pointer solution yet.

Sorting first is what buys the argument. That costs O(n log n) — so say "O(n log n) overall, dominated by the sort", not "O(n)", when you sorted the input yourself.

02 — recognise it

Reaching for it on a problem you have never seen

Recognition is the skill that actually gets tested. Four families of wording point here:

  • Sorted, or cheap to sort, and you need a pair, triplet or quadruplet hitting a target — or a count of pairs satisfying an inequality.
  • Both ends inward: palindromes, containers between two walls, squares of a sorted array.
  • In place, O(1) extra space: remove duplicates, move zeroes, partition, dedupe, "without allocating another array".
  • Two sorted sequences: merge them, or check one is a subsequence of the other.

Read the constraints before you choose

Input size tells you the complexity you are allowed, which usually names the pattern for you.

Telling it apart from its look-alikes

This is where most people lose the problem — not in the coding, but in reaching for the neighbouring pattern. One question separates the two that get confused most:

The discriminator Does the data between the pointers matter? If you need the contents of the span — its character counts, its running sum — that is a sliding window, and both pointers move the same way. Two pointers cares only about the two endpoints, or about a write frontier. It reads the ends, not the middle.
PatternReach for it whenTell
Two pointersSorted input, a relationship between two elements, or an in-place rewriteEndpoints matter, the middle does not
Hash mapUnsorted input and you must return original indicesSorting would destroy the answer
Sliding windowA contiguous subarray or substring with a running constraintBoth pointers move the same direction; you keep window state
Binary searchOne sorted array, locating a single value or a boundaryYou halve the range, you do not walk it

That last row hides the classic trap. Two Sum (LeetCode 1) is unsorted and wants indices, so it is a hash-map problem. Two Sum II (LeetCode 167) is sorted and wants positions in that sorted array, so it is this pattern. Same name, different tool — sorting the first one scrambles exactly what it asks you to return.

Drill: name the pattern before you code

Mixed practice is the part that transfers. Reading a worked solution builds recognition far more slowly than being forced to choose. Decide on each, then reveal.

03 — implement it

Five shapes, and how to pick one

"Two pointers" is an umbrella. In an interview, name the specific shape you are using — it shows you know there is more than one. These five cover essentially every problem in the tier.

A

Converging — pointers walk toward each other

Use for: sorted pair search, palindromes, container problems, any both-ends comparison. The pointers start at opposite ends and close in.

Invariant The answer, if it exists, lies within nums[left..right]. Every move discards only pairs proven impossible.
def two_sum_sorted(nums: list[int], target: int) -> list[int]:
    left, right = 0, len(nums) - 1
    while left < right:                 # strict: a pair needs two distinct indices
        current = nums[left] + nums[right]
        if current == target:
            return [left, right]        # LeetCode 167 is 1-indexed: [left+1, right+1]
        if current < target:
            left += 1                   # need a bigger sum
        else:
            right -= 1                  # need a smaller sum
    return []
Time O(n)Space O(1)

The same skeleton with a skip rule handles Valid Palindrome, where non-alphanumeric characters are stepped over rather than compared. Watch the pointers skip:

Valid Palindrome · "Ab, Ba!"LeetCode 125
def is_palindrome(s: str) -> bool:
    left, right = 0, len(s) - 1
    while left < right:
        if not s[left].isalnum():
            left += 1                   # skip, re-check the loop condition
        elif not s[right].isalnum():
            right -= 1
        else:
            if s[left].lower() != s[right].lower():
                return False
            left += 1
            right -= 1
    return True
Time O(n)Space O(1)

Note the shape: each skip is an elif branch of the same loop, not a nested while. That is deliberate, and section 04 shows the crash you get from the nested version.

B

Read / write — same direction, different speeds

Use for: in-place edits that keep order — remove duplicates, remove an element, move zeroes. A fast read pointer scans everything; a slow write pointer marks where the next kept value belongs.

Invariant Everything before write is already correct and final. Everything from read onward is untouched. The gap between them is junk to be overwritten.
Move Zeroes · keep order, O(1) spaceLeetCode 283
def move_zeroes(nums: list[int]) -> None:
    write = 0                           # nums[0:write] are the non-zeros, in order
    for read in range(len(nums)):
        if nums[read] != 0:
            nums[write], nums[read] = nums[read], nums[write]
            write += 1
Time O(n)Space O(1)Mutates in place, returns None

Swapping, not copying. A copy-forward version leaves stale values in the tail — a real bug, dissected in 04. The swap places the zero where the non-zero came from, so the array stays a permutation of itself at all times.

Remove Duplicates from a sorted array (LeetCode 26) is the same shape with the comparison changed to nums[read] != nums[write], returning write + 1 as the new length.

C

Three-way partition — the Dutch national flag

Use for: sorting into three buckets in one pass — 0/1/2, or below / equal / above a pivot. Three pointers carve the array into four regions.

Invariant [0, low) is all 0s · [low, mid) is all 1s · (high, end] is all 2s · [mid, high] is still unknown. The loop runs until the unknown region is empty.
Sort Colors · one pass, no countingLeetCode 75
def sort_colors(nums: list[int]) -> None:
    low, mid, high = 0, 0, len(nums) - 1
    while mid <= high:                  # <= : index high is still unclassified
        if nums[mid] == 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low += 1
            mid += 1                    # the swapped-in value came from behind: already a 1
        elif nums[mid] == 1:
            mid += 1
        else:
            nums[mid], nums[high] = nums[high], nums[mid]
            high -= 1                   # mid does NOT move: the new value is unexamined
Time O(n)Space O(1)

Two asymmetries carry the whole algorithm, and both are worth saying out loud in an interview. The loop is <=, not <. And mid advances after a 0-swap but not after a 2-swap, because a 0-swap pulls in a value from the already-scanned region while a 2-swap pulls one in from the unknown region.

D

Fix one, two-pointer the rest — k-sum

Use for: triplets and quadruplets. Sort, pin the outer element with a loop, then run shape A on the remaining suffix. For k-sum generally: k − 2 nested loops wrapping one converging pass, giving O(nk−1).

Duplicate handling is the entire difficulty. Watch where the skips fire:

3Sum · input sorted to [-4,-1,-1,0,1,2]LeetCode 15
def three_sum(nums: list[int]) -> list[list[int]]:
    nums.sort()
    n, results = len(nums), []
    for i in range(n - 2):
        if nums[i] > 0:
            break                       # sorted: no zero-sum triplet can start positive
        if i > 0 and nums[i] == nums[i - 1]:
            continue                    # dedup 1: same anchor as last time
        left, right = i + 1, n - 1
        while left < right:
            total = nums[i] + nums[left] + nums[right]
            if total < 0:
                left += 1
            elif total > 0:
                right -= 1
            else:
                results.append([nums[i], nums[left], nums[right]])
                left += 1
                right -= 1
                while left < right and nums[left] == nums[left - 1]:
                    left += 1           # dedup 2: identical left partner
                while left < right and nums[right] == nums[right + 1]:
                    right -= 1          # dedup 3: identical right partner
    return results
Time O(n²)Space O(1) beyond the outputSort included in the n² bound

Three dedup points, and you need all three. Both inner skips are guarded by left < right — without that guard they walk off the end of a uniform array like [0,0,0,0].

E

Two sequences — one pointer each

Use for: merging two sorted arrays, checking a subsequence, intersecting sorted lists. One pointer per input, advanced independently by the comparison.

Invariant (for an in-place merge) Write from the back. The tail of nums1 is spare capacity, so a backward write can never clobber a value you have not read yet.
def merge(nums1: list[int], m: int, nums2: list[int], n: int) -> None:
    p1, p2, write = m - 1, n - 1, m + n - 1
    while p2 >= 0:                      # nums2 exhausted ⇒ the rest of nums1 is already in place
        if p1 >= 0 and nums1[p1] > nums2[p2]:
            nums1[write] = nums1[p1]
            p1 -= 1
        else:
            nums1[write] = nums2[p2]
            p2 -= 1
        write -= 1


def is_subsequence(s: str, t: str) -> bool:
    i = 0
    for ch in t:                        # always advance t; advance s only on a match
        if i < len(s) and s[i] == ch:
            i += 1
    return i == len(s)
merge: O(m+n) / O(1)is_subsequence: O(|t|) / O(1)

04 — where it breaks

The bugs, with their actual wrong answers

Every variant below was run. The "produces" column is real output, not a guess — which is the point: each bug fails on a specific small input you can keep in your head and test against.

1 · while left <= right in a pair search

With <= the pointers can land on the same index, and the element pairs with itself. The answer looks plausible and is wrong.

Buggy · nums=[1,2,3,4], target=8returns [3, 3] — that is 4 + 4, using index 3 twice
Correct · while left < rightreturns [] — no valid pair exists

2 · Skipping with a nested while and no bound check

Writing the palindrome skips as inner while loops without re-checking left < right lets a pointer run off the end of the string.

Buggy · s=".,"IndexError: string index out of range
Correct · elif branchesreturns True — a string with no alphanumerics is a palindrome

3 · while mid < high in the partition

The element sitting at high never gets classified, so the last slot keeps whatever happened to land there.

Buggy · [2,0,1]leaves [1, 0, 2] — not sorted
Correct · while mid <= high[0, 1, 2]

4 · Advancing mid after a 2-swap

The value swapped in from the right end has never been looked at. Stepping over it leaves it misplaced. This one is nasty because it passes on many inputs — [2,0,1] happens to come out right, which is exactly how it survives a casual test.

Buggy · [1,2,0]leaves [1, 0, 2] — not sorted
Correct · hold mid after a 2-swap[0, 1, 2]

5 · 3Sum with no duplicate skipping

The pointers find the same triplet through different index paths. The problem demands unique triplets, so this fails the judge while looking correct in a quick read.

Buggy · [-1,0,1,2,-1,-4][[-1,-1,2], [-1,0,1], [-1,0,1]]
Correct · three skip points[[-1,-1,2], [-1,0,1]]

6 · Move Zeroes by copying instead of swapping

Copying non-zeros forward without zero-filling the tail leaves the original values stranded there. The prefix is right, which makes the bug easy to miss.

Buggy · [0,1,0,3,12][1, 3, 12, 3, 12] — tail never cleared
Correct · swap[1, 3, 12, 0, 0]

7 · Merging two sorted arrays front-to-back, in place

Writing forward into nums1 overwrites values you still need to read. One value is lost and another duplicated.

Buggy · nums1=[1,2,3,0,0,0], nums2=[2,5,6][1, 2, 2, 2, 5, 6] — the 3 is gone
Correct · write from the back[1, 2, 2, 3, 5, 6]

8 · Sorting, then returning indices

The classic Two Sum trap. Sorting produces a correct pair of values at positions that no longer mean anything in the original array.

Buggy · nums=[3,2,4], target=6returns [0, 2] — indices into the sorted copy
Correct · hash map on the original[1, 2]

Two Python-specific costs that hide inside a loop

list.pop(0) and del nums[0] shift every remaining element, so they are O(n), not O(1). Draining a 60,000-element list that way took 266 ms against 8 ms for an index scan — about 32× slower, and it silently turns your O(n) solution into O(n²). Slicing like nums[1:] copies, with the same effect. Use indices, or collections.deque if you truly need to pop from the front.

And never mutate a list while iterating over it. for x in nums: nums.remove(x) on [0,0,1] returns [0,1] — the iterator's cursor skips an element every time the list shifts under it.

The edge-case pass, before you say "done"

Run these against your code in your head — out loud, in an interview. Each is a real failure mode for this pattern, not a generic checklist.

    Follow-ups your interviewer already has loaded

    • "What if the input isn't sorted?" Sort it if order does not need preserving — O(n log n), and say so. If the answer is a pair of original indices, switch to a hash map: O(n) time, O(n) space.
    • "Can you do it in O(1) extra space?" Yes for shapes A, B and C. Note that sorting itself costs O(log n) to O(n) stack space, so "I sorted, therefore it is not truly O(1)" is the honest answer.
    • "Extend it to k-sum." k − 2 nested loops around one converging pass, dedup at every level, O(nk−1).
    • "Why is moving the shorter wall safe?" (Container With Most Water.) Moving either pointer shrinks the width, so the area can only improve if the height rises. Height is capped by the shorter wall — moving the taller one leaves that cap in place and loses width, so it can never help. Only the shorter wall has upside.
    • "Does this overflow?" Not in Python — integers are arbitrary precision. In Java or C++, left + right and area products can overflow 32-bit. Saying this unprompted reads as production experience.

    The stretch anchor, worked

    Trapping Rain Water is the problem that proves you understand invariants rather than templates. Water above index i is min(max height to its left, max height to its right) − height[i]. The obvious solution precomputes both max arrays in O(n) space. The two-pointer version needs neither.

    The insight: when height[left] < height[right], there is already a wall on the right taller than height[left]. So the left side is the binding constraint and the water at left is exactly left_max − height[left] — the exact right-hand maximum is irrelevant, you only need to know it is bigger. Process the shorter side first and its answer is final.

    Trapping Rain Water · total 6LeetCode 42
    def trap(height: list[int]) -> int:
    if not height:
        return 0
    left, right = 0, len(height) - 1
    left_max, right_max = height[left], height[right]
    water = 0
    while left < right:
        if left_max < right_max:        # left side is the binding constraint
            left += 1
            left_max = max(left_max, height[left])   # refresh BEFORE measuring
            water += left_max - height[left]
        else:
            right -= 1
            right_max = max(right_max, height[right])
            water += right_max - height[right]
    return water
    Time O(n)Space O(1)Verified: [0,1,0,2,1,0,1,3,2,1,2,1] → 6 · [4,2,0,3,2,5] → 9

    The order inside each branch matters. Refresh the max, then measure — do it the other way round and the running total can go negative at a new tallest bar. On [4,2,0,3,2,5] that mistake returns 8 instead of 9.

    One-page recall

    Reach for it when

    • Sorted, or cheap to sort
    • A pair, triplet or k-tuple to a target
    • Palindrome or both-ends comparison
    • In place, O(1) extra space
    • Merge or compare two sorted inputs
    • Maximise something between two boundaries

    Reach elsewhere when

    • Contiguous span with running state → sliding window
    • Unsorted and needs indices → hash map
    • Single target in sorted data → binary search
    • Cycle or middle of a linked list → fast/slow (Day 2)

    Say this in the room

    • Name the shape: "converging pointers"
    • State the invariant before coding
    • Justify the move: what does it discard?
    • Brute force first, then the optimisation
    • Dry-run one example plus one edge case
    • Give the honest complexity, sort included

    Check before "done"

    • < vs <= — deliberate?
    • Does every branch move a pointer?
    • Empty, single element, all equal
    • Dedup guarded by left < right
    • Did sorting destroy something needed?
    • No pop(0) or slicing in the loop
