3Sum Dissected

3Sum is not a new pattern. It is Two Sum II run once per element — a reduction you already know. What makes it a Medium is the bookkeeping that keeps the answers unique, and that bookkeeping is where almost everyone loses the problem.

LeetCode 15 O(n²) time · O(1) space Anchor problem n ≤ 3000
01 — the reduction

Pin one number and the rest is Two Sum

The brute force is three nested loops: O(n³), about 27 billion operations at the problem's limit of n = 3000. Far too slow. But look at what happens when you fix the first element.

If the triplet must sum to zero and you have committed to nums[i], then the other two must sum to −nums[i]. That is Two Sum with a target — and on a sorted array, you solve that with converging pointers in one pass. Run it once per anchor and you have O(n²).

One anchor, one Two Sum sub-problemclick a row

Why sorting first is doing three jobs at once

  • It enables the elimination. Converging pointers only work because a sorted order means "sum too small" proves the small end is useless.
  • It puts duplicates next to each other. That is what makes skipping them an O(1) neighbour check rather than a set lookup.
  • It canonicalises each triplet. Every answer comes out in ascending order, so two triplets are equal exactly when they look equal. No sorting inside the comparison.

Sorting costs O(n log n), which vanishes next to the O(n²) scan. And note what you are allowed to lose by sorting: 3Sum asks for the triplet values, not their original indices. That is precisely why sorting is legal here and illegal in Two Sum.

What each guard is actually for

Guard 1, the anchor. If two anchors hold the same value, the second one searches a smaller suffix of the same array and re-finds triplets the first already collected. Skipping repeated anchors is not an optimisation — it is required.

Guards 2 and 3, the inner pointers. Within a single anchor's sweep, the same pair of values can be reached through different indices. On [-2, 0, 0, 2, 2] the anchor -2 finds (0, 2) at indices (1, 4) and again at (2, 3) — one triplet, two paths.

The part nobody tells you A triplet is pinned down by any two of its three values — fix the anchor and the left value, and the right value is forced to be −anchor−left. So deduping the anchor plus either inner pointer is already enough to guarantee uniqueness. Over 3000 random arrays with heavy duplicates, anchor + left alone and anchor + right alone each emitted zero duplicates. Keep both anyway: they cost nothing, they read symmetrically, and the argument for dropping one is not something you want to be reconstructing under interview pressure.

04 — the direction trap

Why the anchor skip looks backwards

The anchor guard is written nums[i] == nums[i-1] — comparing with the element behind. Reaching for nums[i] == nums[i+1] feels equally natural and is wrong. The difference is which copy of a repeated value survives.

  • nums[i] == nums[i-1] keeps the first copy, which sees the largest suffix — including all the other copies of itself.
  • nums[i] == nums[i+1] keeps the last copy, whose suffix no longer contains its own duplicates. Any triplet needing two of that value is gone.

On the classic input this quietly loses a triplet:

Anchor guardOutput on [-1,0,1,2,-1,-4]Over 3000 random arrays
nums[i] == nums[i-1][[-1,-1,2], [-1,0,1]]correct every time
nums[i] == nums[i+1][[-1,0,1]] — lost [-1,-1,2]wrong on 1758 / 3000

It is a perfect example of a bug that survives casual testing: it returns a correctly-formed, plausible-looking list. Only an input where a triplet needs two copies of the anchor value exposes it — which is exactly the input the LeetCode example uses.

Two other decisions worth being able to defend

Moving both pointers after a hit. Once you have recorded a triplet, neither endpoint can appear in another triplet with this anchor — the partner of each is uniquely determined, and you just used it. Advancing only one still gives correct output if your dedup is right, but it wastes work: on a 300-element array, moving both took 4,760 inner steps against 5,225.

The nums[i] > 0 break. The array is sorted, so once the anchor is positive every remaining element is too, and three positives cannot sum to zero. This is an optimisation, not a correctness guard — removing it changed no answer across all 3000 test arrays. Say that distinction out loud; it shows you know which lines you can afford to lose.

05 — the cost

Where the n² comes from

Each anchor runs one converging pass over what is left to its right. Anchor 0 sweeps n−1 elements, anchor 1 sweeps n−2, and so on. Stack those sweeps and you get a triangle — half of an n×n square.

Inner sweep length per anchor · n = 10sum ≈ n²/2

Total ≈ n²/2 pointer moves. The sort adds O(n log n), which is smaller and disappears into the bound.

Measured on random arrays, counting actual inner-loop iterations — the guards and the early break make real runs come in under the worst case, and doubling n reliably quadruples the work:

06 — write it from memory

The whole thing, annotated

def three_sum(nums: list[int]) -> list[list[int]]:
    nums.sort()                                    # enables elimination + groups duplicates
    n, results = len(nums), []

    for i in range(n - 2):
        if nums[i] > 0:
            break                                  # optimisation: three positives cannot reach 0
        if i > 0 and nums[i] == nums[i - 1]:
            continue                               # GUARD 1 — compare BACKWARD, keep the first copy

        left, right = i + 1, n - 1                 # Two Sum on the suffix, target = -nums[i]
        while left < right:
            total = nums[i] + nums[left] + nums[right]
            if total < 0:
                left += 1                          # need more
            elif total > 0:
                right -= 1                         # need less
            else:
                results.append([nums[i], nums[left], nums[right]])
                left += 1
                right -= 1                         # both: each endpoint's partner is used up
                while left < right and nums[left] == nums[left - 1]:
                    left += 1                      # GUARD 2 — same left value, same triplet
                while left < right and nums[right] == nums[right + 1]:
                    right -= 1                     # GUARD 3 — same right value, same triplet

    return results
Time O(n²)Space O(1) beyond the outputSorting is O(n log n), dominated

Both inner while loops are guarded by left < right. Without it, an array like [0,0,0,0] walks a pointer straight off the end.

The other style you will meet

Many write-ups skip duplicates before advancing rather than after. It is the same algorithm — verified identical on 3000 arrays — so recognise it, pick one, and stay consistent:

            else:
                results.append([nums[i], nums[left], nums[right]])
                while left < right and nums[left] == nums[left + 1]:
                    left += 1                      # look FORWARD, then step off the run
                while left < right and nums[right] == nums[right - 1]:
                    right -= 1
                left += 1
                right -= 1

Narrating it in the room

"Brute force is three nested loops, O(n³) — too slow at n = 3000. But if I fix one element, the rest is Two Sum with target minus that element, and on a sorted array Two Sum is a linear converging-pointer scan. So: sort, then for each anchor run that scan. That is O(n²), with O(n log n) for the sort underneath it."

"The problem wants unique triplets, so I need to skip duplicates in three places — repeated anchors, and repeated values at each pointer after recording a hit. Sorting is what makes those neighbour checks work. Let me dry-run [-1,0,1,2,-1,-4], and also check [0,0,0,0] so the skip loops can't run off the end."

Recall card

The skeleton

  • Sort
  • For each anchor i: break if positive; skip if same as i−1
  • Converge left, right over the suffix
  • On a hit: record, move both, skip both runs

Three guards

  • nums[i] == nums[i-1] — backward, keeps the first copy
  • nums[left] == nums[left-1] after a hit
  • nums[right] == nums[right+1] after a hit
  • Both inner loops need left < right

Edge cases to state

  • [], [0], [0,0] → empty
  • [0,0,0,0] → one triplet, not four
  • All positive or all negative → empty
  • Negatives everywhere — the break relies on sortedness

If you forget a guard

  • No anchor skip → repeated triplets across anchors
  • No inner skip → repeated triplets inside one anchor
  • Forward-looking anchor skip → missing triplets
  • No left < right on the skips → index error
