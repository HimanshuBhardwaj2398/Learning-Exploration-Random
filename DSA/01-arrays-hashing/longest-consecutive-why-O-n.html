Why it's O(n), not O(n²)

There's a loop inside a loop here — the classic shape of a quadratic algorithm. Yet this one is linear. The reason is amortization: no matter the input, each number is touched a constant number of times. Step through it and watch the operation counter — it never crosses the 2n line.

02
The amortized argument

    
A worst-case-per-line reading over-counts. The honest way to bound a nested loop is to ask how much total work happens across the whole run, then divide by n.


    

      

        
1The guard is everything

        
The inner while only runs when n-1 is absent from the set — i.e. when n is the first number of a consecutive run. Every run has exactly one such starting number.

        
So the expensive walk fires once per run, never once per element.

      

      

        
2Walks don't overlap

        
The walk from a run's start steps through that run's numbers and only those. Different runs are disjoint sets of integers, so no number is ever walked over twice.

        
Sum the lengths of all the walks and you get n — the total count of numbers, once each.

      

      

        
3Charge the cost to elements

        
Give every number a budget of 2 checks: one for its own n-1 not in set test in the outer loop, one for being the target of a single walk step.

        
Total checks ≤ 2n. That's the meter you watched fill.

      

      

        
4Add the setup

        
Building set(nums) is one O(n) pass. Set lookups are O(1) on average, so each check is constant.

        
O(n) + O(2n) = O(n) time. The set itself is O(n) space.

      

    


    
The trap: reading a nested loop as O(n²) by reflex. The upper bound "n outer iterations × up to n inner iterations" is real but loose. When a guard makes the inner work fire only on run-starts, and those runs partition the input, the true bound collapses to linear.

  


  

    
03
Linear vs. the naive walk-from-everything

    
Without the n-1 guard, you'd start a walk from every element and re-traverse whole runs repeatedly — the genuine O(n²). Here's how the two diverge as the input grows.

    

      

         guarded scan — 2n
         naive walk-from-all — n²
      

      
      
At n = 60 the guarded scan does ~120 checks; the naive version does ~3,600 — a 30× gap that widens without bound.

    

  


  

    
The one caveat worth stating in an interview. The O(n) rests on hash-set membership being O(1) average. Python's set can degrade to O(n) per lookup under adversarial hash collisions, which would make the whole thing O(n²) in a pathological worst case. For the integer keys in this problem that never happens in practice, so the accepted answer is O(n) time, O(n) space — just name the assumption you're leaning on.
