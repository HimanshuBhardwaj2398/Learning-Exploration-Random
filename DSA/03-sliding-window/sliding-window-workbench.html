Sliding Window Workbench
Pattern 03 · Day 1 · arrays & strings

The window that never goes backwards

Two pointers taught you to move pointers toward each other and throw away candidates. Sliding window keeps both pointers moving the same way and cares about everything between them. That one change is the whole pattern — and it is why the cost stays O(n).

1

Spot it

Trigger words, constraints, look-alikes

Sliding window is for one shape of question: find a contiguous run — subarray or substring — that satisfies a constraint, and report its length, sum, contents or count.

Three signals, all of which have to be present:

  1. Contiguous. The words subarray, substring, consecutive, window of size k. The moment a problem says subsequence, this pattern is out — a window can only ever see an unbroken range.
  2. A constraint you can check in O(1) from some running state: a sum, a count, a character-frequency dict, a set size.
  3. Optimise or count: longest / shortest / maximum / minimum / "how many", or a fixed k.
The condition that makes it legal

Sliding window only works when validity is monotone in the window: if a window is invalid, every window that contains it is also invalid (for "at most" constraints), or growing the window can only push a sum further past the target (for "at least" constraints with non-negative values). That monotonicity is what lets you move start forward and never reconsider it. Break the monotonicity — add a negative number — and the pattern silently returns wrong answers. There's a verified counterexample in stage 6.

What the constraints tell you

A useful reflex: if you can describe your brute force as "for every start, extend to every end", the window is the fix. You are about to reuse almost all of that inner work.

One-line discriminator

Two pointers asks "what's at the ends?" · Sliding window asks "what's inside?" If deleting an element from the middle would change your answer, you're holding a window.

2

See it

Why the cost collapses to O(n)

The brute force recomputes each window from scratch. The window reuses the previous answer and pays only for the difference. That is the entire idea; everything else is bookkeeping.

Take max sum of any subarray of size 3 on [2,1,5,1,3,2]. The naive version adds three numbers for each of the four positions: 12 additions. The window adds one and subtracts one per step: after the first fill, 2 operations per position, regardless of how big k gets. Step through it — watch the sum, not the cells.

LC 643 · fixed length max sum of a window of size k = 3 in [2,1,5,1,3,2]

The amortisation argument, drawn

For variable-length windows the O(n) claim is less obvious: there's a while loop inside a for loop, which looks like O(n²). It isn't, and the reason is worth being able to say out loud in an interview:

The proof in one sentence

start and end each only ever increase, and neither can exceed n. So across the whole run there are at most n extensions and at most n contractions — 2n pointer moves total, each O(1). The inner while can run many times on one iteration, but it is borrowing from a budget that was already paid for.

Each frame of the "longest substring without repeating characters" run on "abcabcbb". Both staircases are non-decreasing — that is the whole proof. The gap between them is the window.

3

The three shapes

Fixed · longest · shortest

Almost every window problem is one of three skeletons. Learn to pick the skeleton from the question in one read, and the code writes itself.

The question says…ShapeWhere the answer is recorded
"of size k", "every k consecutive"FIXEDOnce the window reaches size k, every step
"longest / maximum … such that"LONGESTAfter the shrink loop, when the window is valid
"shortest / minimum … such that"SHORTESTInside the shrink loop, while it's still valid
The single most useful thing on this page

Longest records after shrinking. Shortest records inside the shrinking. Get those two backwards and you get bugs 3 and 7 in stage 5 — both of which return plausible-looking wrong numbers rather than crashing.

Shape A — fixed length

def max_sum_k(nums: list[int], k: int) -> int:
    window = sum(nums[:k])          # pay O(k) once
    best = window
    for end in range(k, len(nums)):
        window += nums[end] - nums[end - k]   # add incoming, drop outgoing
        best = max(best, window)
    return best

The whole trick is nums[end] - nums[end - k]. If you ever find yourself writing sum(nums[i:i+k]) inside a loop, you have re-created the O(n·k) brute force.

Shape B — longest valid window

def longest_valid(seq) -> int:
    state = ...                    # dict / set / counter
    start = best = 0
    for end, item in enumerate(seq):
        add(state, item)           # extend right, O(1)
        while not valid(state):      # while, not if (see stage 5)
            remove(state, seq[start])
            start += 1
        # INVARIANT: window [start, end] is valid here
        best = max(best, end - start + 1)
    return best

Filled in for longest substring without repeating characters. Watch the caption colour: teal steps extend, amber steps contract.

LC 3 · longest longest substring without repeating characters in "abcabcbb" 
def longest_unique(s: str) -> int:
    count = defaultdict(int)
    start = best = 0
    for end, ch in enumerate(s):
        count[ch] += 1
        while count[ch] > 1:                # only ch can be the duplicate
            count[s[start]] -= 1
            if count[s[start]] == 0:
                del count[s[start]]         # keep len(count) honest
            start += 1
        best = max(best, end - start + 1)
    return best

Note while count[ch] > 1 rather than a general validity scan: the only character that can have just become invalid is the one you added. That's an O(1) check instead of an O(window) one.

Shape C — shortest valid window

Same skeleton, two changes: the loop condition becomes while valid (shrink greedily while you still can), and the answer is recorded inside it.

LC 209 · shortest min length subarray with sum ≥ 7 in [2,3,1,2,4,3] 
def min_subarray_len(target: int, nums: list[int]) -> int:
    start = total = 0
    best = float('inf')
    for end, v in enumerate(nums):
        total += v
        while total >= target:              # while VALID, not while invalid
            best = min(best, end - start + 1)  # record INSIDE
            total -= nums[start]
            start += 1
    return 0 if best == float('inf') else best

Returning 0 rather than inf when nothing qualifies is part of the problem statement, and a very common dropped requirement.

4

The need / have counter

The hard-mode variant, made mechanical

Minimum Window Substring (LC 76) is the problem people fear. It is Shape C with a smarter valid() — and one idea that makes it O(n) instead of O(26n): a single integer called missing.

The naive check is "does my window's counter cover every character of t?", which is a dict comparison every step. Instead, keep one counter that starts at Counter(t) and let it go negative:

  • need[ch] > 0 — still short of this character.
  • need[ch] == 0 — exactly covered.
  • need[ch] < 0 — surplus; these are the characters you can safely drop when shrinking.

missing counts how many character slots are still unfilled. Decrement it only when need[ch] was positive before the decrement — that single guard is what makes surplus copies not count. Validity is then missing == 0: an O(1) integer test.

LC 76 · need / have smallest window of "ADOBECODEBANC" containing all of "ABC" 
def min_window(s: str, t: str) -> str:
    if not s or not t: return ""
    need = Counter(t)
    missing = len(t)                       # slots, not distinct chars
    start = 0
    best = (float('inf'), 0, 0)
    for end, ch in enumerate(s):
        if need[ch] > 0: missing -= 1   # guard: surplus doesn't count
        need[ch] -= 1
        while missing == 0:               # valid -> record, then shrink
            if end - start + 1 < best[0]:
                best = (end - start + 1, start, end)
            need[s[start]] += 1
            if need[s[start]] > 0: missing += 1
            start += 1
    return "" if best[0] == float('inf') else s[best[1]:best[2]+1]

The same counter drives LC 438 Find All Anagrams and LC 567 Permutation in String — both are the fixed shape with this state, since the window size is len(p).

Counting windows: the at-most trick

When the question is "how many subarrays have exactly k distinct values", a direct window doesn't work — "exactly k" isn't monotone. The standard move:

exactly(k) = at_most(k) - at_most(k - 1)

and at_most is a clean longest-shaped window. The counting line is the memorable part:

    # every window ending at `end` and starting at >= start is valid
    total += end - start + 1

Verified: on [1,2,1,2,3] with k=2 this gives 7, matching an exhaustive count over all 15 subarrays. Same trick powers LC 992, LC 930 and LC 1248.

5

Eight ways it breaks

Every wrong output below was actually produced

These aren't hypothetical. Each variant was run against the correct version; the numbers shown are real output. Read the bug, predict the failure, then open it.

1Forgetting to subtract the outgoing element in a fixed window 
    window += nums[end]                    # never drops nums[end - k]
max_sum_k([2,1,5,1,3,2], k=3) → got 14 · want 9

Why: the "window" silently became a prefix sum — it grows forever. 14 is 2+1+5+1+3+2. Fix: window += nums[end] - nums[end-k], one statement, both halves.

2Recording the answer before the window reaches size k 
        if end >= k: window -= nums[end-k]
        best = max(best, window)          # partial windows counted too
max_sum_k([-5,-5,-5], k=2) → got -5 · want -10

Why: hides completely on non-negative input — a prefix is never better than the full window there. LC 643 allows values down to −10⁴, so this passes your hand-tests and fails the judge. Fix: only start recording once end >= k-1.

3Longest: recording before shrinking back to valid 
        count[ch] += 1
                best = max(best, end - start + 1)   # window may be invalid NOW
        while count[ch] > 1: ...
longest_unique("abcabcbb") → got 4 · want 3

Why: it measured "abca" — which has a repeat — before the shrink loop fixed it. Fix: record only below the while, where the invariant holds. This is the single most common sliding-window bug.

4Leaving zero-count keys in the state dict 
            count[s[start]] -= 1          # key stays behind with value 0
            start += 1
at_most_k_distinct("aabbcc", k=2) → IndexError: string index out of range · want 4

Why: len(count) is the validity test, and a stale 'a': 0 keeps it above k forever, so the shrink loop runs start off the end of the string. Fix: if count[c] == 0: del count[c]. If your state is a dict whose size is the condition, deletion is not optional.

5Jumping start to last_seen + 1 without the max() guard 
        if ch in last:
            start = last[ch] + 1          # start can move BACKWARDS
longest_unique("abba") → got 3 · want 2

Why: at the final 'a', last['a'] = 0, so start jumps back to 1 — behind where it already was — and the window re-swallows a 'b'. Fix: start = max(start, last[ch] + 1). The optimisation is fine; it just has to respect the one rule of this pattern: pointers never go backwards.

6Shortest: recording after the shrink loop instead of inside it 
        while total >= target:
            total -= nums[start]; start += 1
                best = min(best, end - start + 1)   # window is invalid here
min_subarray_len(7, [2,3,1,2,4,3]) → got 1 · want 2

Why: the loop exits precisely when the window stopped qualifying, so you measure a window whose sum is below target. Fix: record inside the loop, before the shrink step. Mirror image of bug 3 — and note both return a number, never an exception.

7Window length written as end - start 
        best = max(best, end - start)      # missing the + 1
longest_unique("abcabcbb") → got 2 · want 3

Why: both indices are inclusive, so the count is end - start + 1. Fix: sanity-check on a single element: start == end must give length 1.

8Using the window at all when values can be negative 
# min length subarray with sum >= target, nums contains negatives
        while total >= target: ...
nums = [-3, 2, -3, 0, 2, -3, -4], target = 1 → got 0 · want 1

Why: the window assumes extending can only raise the sum. With a negative ahead, a window you already discarded could have become valid later, so shrinking is no longer safe. Found by fuzzing the window against brute force over 20,000 random arrays. Fix: prefix sums + a monotonic deque (LC 862). Ask about negatives in the interview — it is one of the highest-signal clarifying questions you can ask on this pattern.

The if vs while question, settled

People will tell you "always use while to shrink". That's safe advice, but the real answer is more interesting, and knowing it is a strong signal in an interview. Swapping while for if in the shrink step was tested exhaustively:

ShapeFailuresVerdict
LONGEST — at most k distinct0 / exhaustive*if is correct
SHORTEST — min subarray ≥ target1981 / 6000while required
COUNTING — number of valid windows2304 / 6000while required

*All strings over {a,b,c} up to length 8, for k ∈ {1,2,3}, plus 6000 random cases.

Why longest survives

With if, the window grows by one and shrinks by at most one each step, so its length is a high-water mark: it never drops below the best valid length found so far. The window may be momentarily invalid, but its length is still a valid answer from earlier — so the maximum comes out right. This is the "non-shrinking window" optimisation. Shortest and counting read the window's current contents, so they need it genuinely valid: while.

Practical advice: write while every time. But if an interviewer asks whether if would work, the answer "for the longest variant yes, because the window length is monotone; for shortest no" is the one that lands.

6

When it's the wrong tool

Recognising the boundary
Negatives break monotonicity

Every "shrink while valid" argument assumes that removing an element can only move you away from validity. Introduce negatives and that fails — which is why LC 560 (subarray sum equals k) uses prefix sums and a hash map, not a window, even though it looks like a window problem. Whenever a problem allows negative numbers and asks about sums, reach for prefix sums.

Looks like a window, isn'tLCUse instead
Count subarrays with sum exactly k (negatives allowed)560Prefix sum + hash map
Shortest subarray with sum ≥ k (negatives allowed)862Prefix sum + monotonic deque
Max value in every window of size k239Window + monotonic deque
Longest subsequence with a property300DP — a window can't skip elements
Median of every window of size k480Window + two heaps / sorted list

Pattern within the pattern: when the window's state needs to answer "what's the max / median in here?", a dict can't do it, and you bolt a deque or heap onto the same skeleton. The window machinery survives; only add and remove get smarter.

    Saying it out loud

    The narration that scores

    The strongest signal in a coding round is the journey: brute force → the exact wasted work → the observation that removes it. Teleporting to the optimal answer reads as memorisation.

    1. Clarify first. "Can values be negative?" and "can the window be empty?" — on this pattern those two questions decide whether a window is even legal.
    2. State the brute force and its cost. "For every start, extend to every end — O(n²), and with an O(n) validity check inside, O(n³)."
    3. Name the waste. "When I move the start forward I rebuild almost the same window I just had."
    4. State the invariant. "I'll keep [start, end] valid at the bottom of each iteration, so the length there is always a legal candidate."
    5. Justify O(n) explicitly. "The inner while looks quadratic, but start only ever advances, so it's 2n moves total — amortised O(n)."
    6. Test out loud: empty input, single element, k larger than the array, all-identical values, and the no-valid-window case.
    Micro-narration to rehearse

    "Contiguous substring, longest, constraint I can check from a counter — that's a variable sliding window, longest shape. I extend end, and while the window is invalid I drop from start. I record the length after the shrink loop, where the window is guaranteed valid. Both pointers only move forward, so O(n) time; the state holds at most 26 keys, so O(1) space."

    Recognise

    contiguous subarray / substring · longest–shortest–exactly–at most · window of size k · constraint checkable in O(1) from running state.

    Counting

    total += end - start + 1          # windows ending at end
exactly(k) = at_most(k) - at_most(k-1)

    Traps

    end - start + 1, never end - start · delete zero-count keys · longest records after shrinking, shortest inside · start never moves backwards (max() guard on index jumps) · fixed windows subtract the outgoing element · return 0 / "" when nothing qualifies · negatives invalidate the whole approach · state must support O(1) add, remove and validity check.

    Complexity to state

    Time O(n) — each index enters and leaves the window once, 2n pointer moves. Space O(k) or O(alphabet); say O(1) when the alphabet is fixed at 26 and mean it.
